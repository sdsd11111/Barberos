# Objetivo

Definir cómo se siente usar BarberOS, para dos audiencias distintas: el dueño de la barbería (panel) y el cliente final (WhatsApp).

---

# Principio rector

El dueño de barbería no quiere aprender un software. La promesa central del producto es: *"No necesitas usuario ni contraseña, ni aprender un dashboard."* Toda decisión de UX se mide contra esa promesa.

---

# Experiencia del cliente final (vía WhatsApp)

No existe app que descargar. No existe login. El flujo completo:

1. El cliente escanea un QR o recibe el link directamente.
2. Recibe un mensaje de WhatsApp con su progreso visual: `[███░░] 3 de 5`.
3. Al llegar al quinto corte, recibe el mensaje de premio.
4. Se le pide una calificación simple (1-5) por el mismo canal.

No hay pantallas. No hay fricción. El canal es uno que el cliente ya usa a diario.

# Experiencia del dueño (Panel)

## Principio: "Sin dashboard que aprender"

El panel existe para dos acciones diarias, no para navegar reportes complejos:

1. Registrar un corte (modal simple: número de WhatsApp + barbero).
2. Aprobar o rechazar check-ins entrantes (cola de aprobación con polling en tiempo real).

Todo lo demás (clientes, historial, métricas) es secundario y de consulta, no de uso diario obligatorio.

## Cola de aprobación (Anti-fraude)

Cada check-in vía WhatsApp entra como `PENDING`. El dueño recibe una notificación push nativa en su celular (Sprint 8, 2026-07-21) con sonido, incluso si el panel está cerrado. Al abrir el panel, ve la cola visual tipo bandeja y aprueba o rechaza con un toque.

**Mecanismo real (confirmado por versión del hijo, 2026-07-22):** Push nativo con sonido como canal primario, cola visual como fallback cuando el panel está abierto. Detalle técnico completo de la especificación pendiente de confirmar con el hijo.

Este mecanismo evita que un cliente reporte visitas falsas y le da al dueño una sensación de control real sobre lo que se registra — refuerza directamente el eje emocional de "control", no solo la integridad técnica del dato.

## Identidad visual (cinematográfica) — Sistema de Rediseño (Sprint E, 2026-07-29)

A partir del Sprint E, el panel del dueño se construye sobre el sistema de componentes premium descrito en [[13-COMPONENTES]] sección "Sistema de Rediseño Visual". La identidad base se conserva pero ahora se aplica de forma sistemática:

- **Fondo:** negro cálido (`#0a0807`), no negro puro — transmite calidez, no frialdad de software corporativo.
- **Texto principal:** crema (`#f3ece1`).
- **Texto secundario:** `#a89e90` (subtítulos, captions).
- **Texto terciario:** `#5c554c` (labels desactivados).
- **Acento primario:** naranja cobrizo (`#d97644`) — cálido, artesanal, coherente con el oficio de barbería. Usado en CTAs, valores destacados, estado activo.
- **Acento secundario:** ámbar/dorado (`#e8a33d`) — hover, anillos de progreso, gradientes.
- **Acento positivo:** verde (`emerald-400` / `#4ADE80`) — **SOLO** para indicadores positivos. Nunca decoración.
- **Bordes sutiles:** `#3a2f25` / `#2a2520` — coherentes con el fondo carbón.
- **Tipografías:** Fraunces (serif display, con carácter editorial) + Space Grotesk (sans body) + JetBrains Mono (etiquetas uppercase, datos, códigos, métricas).
- **Glassmorfismo:** tarjetas con `bg-[#1a1614]/70` + `backdrop-blur` sutil + borde `border-[#3a2f25]/80` + sombra exterior. Línea de luz decorativa en el top (gradiente `via-[#f3ece1]/15`).
- **Hero:** imagen real de fondo + degradado vertical oscuro que se funde con `#0a0807` + degradado lateral reforzado en desktop + viñeta naranja sutil.
- **Tabs:** píldora / segmented control (variante `pill`) con tabs circulares en la navegación inferior flotante.
- **Botones:** píldora con tres variantes (`primary` / `ghost` / `outline`), tipografía monoespaciada uppercase con tracking `[0.18em]`.

Esta identidad diferencia a BarberOS de la estética típica de SaaS genérico (azul corporativo, sans-serif neutro) y refuerza el posicionamiento premium descrito en [[10-ROADMAP-COMERCIAL]] y [[15-BRAND-KIT-BRIEFING]].

**Regla dura:** los colores de acento, la paleta de fondo y las tipografías **NO cambian** entre componentes, páginas o sprints. Toda inconsistencia visual debe corregirse, no justificarse.

# Principios de interacción

1. **Cero curva de aprendizaje para el cliente final.** Si requiere explicación, está mal diseñado.
2. **Mínimas pantallas para el dueño.** Cada pantalla adicional es fricción que compite contra su tiempo cortando cabello.
3. **Feedback inmediato.** Toda acción (registrar corte, aprobar check-in) debe confirmar visualmente en menos de 2 segundos. El canal primario es push nativo con sonido (Sprint 8); el polling agresivo de versiones anteriores es ahora fallback, no el mecanismo principal.
4. **El progreso siempre visible.** La barra de progreso Unicode es el elemento central de motivación del cliente final — no debe reemplazarse por abstracciones (puntos, niveles) que pierdan la simpleza visual.

# Lo que se evita deliberadamente

- Onboarding con tours guiados o tooltips excesivos — contradice la promesa de simplicidad.
- Cualquier pantalla que obligue al dueño a "configurar" antes de ver valor. El primer corte registrado debe generar valor visible de inmediato.
- Terminología técnica visible al usuario (API, webhook, tenant) — eso vive solo en la documentación interna.
- Componentes del panel que no usen el sistema de rediseño ([[13-COMPONENTES]]). Cualquier bloque sólido apilado sin glassmorfismo es candidato a reemplazo.
- Múltiples CTAs compitiendo en la misma pantalla — una intención por superficie.

## Patrones aprendidos durante el Sprint E (2026-07-29)

- **Server Components con Prisma NO pueden importarse en Client Components.** Si el padre es client, pasar el resultado de Prisma como `children` o `ReactNode` prop.
- **Hidratación de tiempo falla con `toLocaleTimeString`.** Usar `getUTCHours() - 5` (Ecuador = UTC-5) con `suppressHydrationWarning`.
- **`BarberosView.tsx` tiene un error de hidratación preexistente** que no es causado por el rediseño. Mantener `suppressHydrationWarning` hasta investigar.
- **`GlassCard` sobre `PanelHero`** debe usar `elevated` prop para sumar `ring-1 ring-[#d97644]/15` y mantener contraste.
- **`FloatingNav` con `z-40` queda debajo del `ApprovalQueue`** (que usa `z-50`). Mantener este orden para que la cola de aprobación tape la nav cuando esté activa.

# Relación con el Motor de Conocimiento e IA (Premium) — Director IA en producción

El Director General IA está implementado y en producción desde el 2026-07-26 (Sprint D). La interacción se mantiene dentro del patrón conversacional:

- `DirectorWidget` (recomendaciones automáticas en el dashboard) con badge dinámico del modelo en uso y disclaimer de incertidumbre.
- `DirectorChatWidget` (chat libre con el Director IA desde el panel).
- Botones de 1-Clic a WhatsApp para ejecutar recomendaciones sin salir del flujo.
- Regla de Gating por `planType`: cuentas `PRO` ven `UpgradeBanner` decorativo en lugar de pantallas rotas. Ver [[19-INSTRUCCION-MOTOR-DIRECTOR]] sección 1.1.

La promesa original se mantiene: la IA traduce datos en lenguaje conversacional, no agrega pantallas que aprender. El chat del panel convive con las `MetricTile` y `PanelHero` sin reemplazarlas.
